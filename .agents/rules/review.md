# 评审与完成定义规范

适用：所有变更的实施、验证、合并与交付。单人承担产品/开发/测试职责，不视为三位独立评审者。

| 约束 | 检查方式 / 失败判据 |
| --- | --- |
| 每次开发先有proposal/design/spec/tasks及概览，用户敲定范围后实施；新增范围先更新设计。已确认范围内继续同一change，避免重复文档。 | 对照四文档、用户授权与diff；先改实现后补规划，或变更超出确认范围即不满足流程。 |
| Done=Scenario逐项有证据、适用门禁通过、设计与任务同步、规范缺口已标注、交付记录与例外齐全；只有实际完成项可勾选。 | 对照Scenario→任务→测试/人工检查→报告提交号；缺证据、跳过、空结果不能计通过，不为凑完成率归档。 |
| 单次手写业务变更目标≤400行；超出须design说明必要性或拆分。生成文件、锁文件单列，不以其掩盖业务diff。 | git diff --stat及逐文件审查；无理由的大范围改动不合并。基础设施/规范迁移说明范围，不机械拆成重复文件。 |
| 自审逐项查范围、依赖方向、命名、授权、输入校验、响应码/副作用、配置/日志、迁移回滚、文档复现与依赖许可。每条记通过/失败/不适用及理由。 | 至少追一条正常与失败路径；HTTP200不等于成功，错误码正确但泄露或写库也算失败。 |
| 合并必须make check通过；涉及运行行为跑make acceptance，依赖变更跑make audit；老师交付通过sh scripts/grade.sh。失败/网络不可达不豁免成成功。 | 读取实际命令退出码与CI check/grade；必测失败或未执行即阻断，不复用不同提交的报告冒充当前结果。纯文档不新增镜像运行测试，但遵守仓库现有CI门禁。 |
| main禁止强推/删除，经PR和必需CI合并；单人审批数0。验证通过后归档、同步长期spec，再标记已验收版本。 | 查看提交历史、PR、CI与标签；不得绕过门禁或提前宣称GitHub已同步。 |
| 证据放docs/lesson-07或对应课次；记录时间/时区、提交、环境、命令、退出码与限制。报告与截图脱敏，历史报告明确其范围。 | 原始报告与摘要可对照；伪造截图、无来源结果、以GD完成状态代替Plus均失败。 |
| 例外需写原因、影响、替代检查、责任职责与补齐触发点；独立人类评审、异机复验未做就保留未完成。 | 自审或新AI会话不标为独立人类peer review；课程例外是否接受由教师判断。缺陷当日处理或保持未完成。 |


## 下一阶段：AI代码审核准入

- 对每次AI生成初稿，按**接口入口、业务逻辑、数据库操作、公共函数、错误处理、安全与隐私、性能**七类拆读；逐项说明检查结果或N/A理由。
- 用**需求覆盖率、需求一致性、失败路径、查询性能、重复代码、漏洞、高风险场景**七维核对。需求Scenario用已实现/部分实现/未实现；无测量不编覆盖率或重复比例。
- 每个受审文件给出**可用/待修改/风险无效**；待修改须修复重审，风险无效丢弃重写。可用也不免除测试与适用交叉评审。
- 权限、并发、事务、数据一致性逐项记录“查了什么、依据哪条规约、结论与证据”；不得仅填通过。机器能判的用现有扫描/测试，人工复核高风险部分，发现共性问题更新对应规则。
- 每次合入应有`docs/reviews/`对应记录，使用[模板](../../docs/reviews/template.md)。不得直接合入/上线未经审核的AI代码；无独立同学peer review必须标未完成。现有单人配置不等于满足新课件的交叉评审要求，课程适配待教师确认；CI和AI审核不能替代同学。

检查：核对变更→Scenario→逐文件结论→高风险依据→检查结果→交叉评审/例外；缺记录、风险未处理或将未审核当可用均阻断。纯文档可对运行风险记有理由的N/A，但仍保留自审与peer差异。
