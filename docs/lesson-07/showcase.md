# 最终讲稿：用工程基线支撑下一阶段AI代码审核（约6分钟）

括号中的开页提示只用于操作，不用念。详细逐项状态见[核对清单](checklist.md)，规划见[roadmap](../roadmap.md)。介绍主线：做了什么→为什么做→后续怎样实践→怎样算交付。

## 1. 项目和本次展示范围（约40秒）

【打开README】

老师好，我的项目是CampusClaw Plus，面向班级教学，希望把讲义检索、辅助学习、作业批改和错题订正连成一个闭环。它基于之前GD项目的经验独立建设，后续代码和验证都以Plus仓库为准。

目前我已经建立工程基线、规约、八类规范和自动验收。教学业务仍在规划阶段。这次我重点介绍这些准备做了什么、为什么要先做，以及它们如何支持下一阶段审核AI写出的代码。

## 2. 已经做了什么，为什么先做（约1分20秒）

【打开AGENTS，指向八类索引，不逐行朗读】

第一，我完成了独立仓库和可启动的项目骨架。这样后续每次新增功能都有稳定的起点，出了问题能够判断是哪次改动引入的。

第二，我固定了先规划再实施的流程。每次先写为什么做、准备怎么做、怎样验收和具体任务这四份文档，确认后才开始实现。这样审核时有明确标准，也能减少AI在需求不清时扩展范围。

第三，我整理了八类规范，覆盖产品、后端、安全、测试、运维、AI、数据和评审。它们通过AGENTS提供入口，相关规则按任务读取；常驻约束与按场景执行的流程分开，既能持续约束生成，也控制上下文长度。

第四，我建立了Docker自动验收、报告和PR检查门禁。这样别人能复验，失败和缺证据也不会被当成通过。自动检查处理可重复判断的问题，人工审核仍需关注业务逻辑和高风险边界。

## 3. 怎样证明规范不只是写在文件里（约50秒）

【打开核对表C项或verification记录】

我对照之前的评分标准，把入口和加载方式、八类覆盖、可判定检查、组织与追溯逐项对应到了仓库文件。

其中，可判定性会用故意违反规则的方式检查：例如让服务层出现不允许的依赖，或者把未开放接口改成成功放行，检查程序应当失败；恢复之后再通过。这样可以证明这些检查至少能够发现它们针对的问题，而不只是在正常流程上跑绿。

报告也写明提交和范围。骨架验收通过不能替代未来业务测试，规则文件存在也不能替代新的加载复验和人工评审。

## 4. 后续功能怎么与审核实践结合（约1分20秒）

【打开项目规划】

下一阶段我先做班级知识库，优先检查谁能访问哪份资料，以及上传失败后会不会留下不一致的数据。

然后增加AI应用、提示词、技能和外部工具，重点检查实际发送给模型的内容是否符合绑定和权限，引用是否真实，工具或模型失败时是否有明确处理。

再做作业、批改复核和错题订正，重点练重复提交、并发、事务和数据一致性。例如未来要求一次提交不能产生重复结果，我会先说清要保证什么，再检查它靠什么机制保证，构造同时请求或中途失败，最后证明修复后的结果符合规约。这个例子是未来实践目标，当前Plus还没有实现作业功能。

最后再基于真实事件做学情统计和部署交付，核对统计来源、查询风险和恢复能力。

## 5. 审核怎样形成固定流程（约1分钟）

【打开评审规范和模板】

我已把新课件的要求写进评审规则和表格。审核时按七类对象拆开阅读，再按需求、失败路径、性能、重复、漏洞和高风险等维度给出结论，不只记录“运行成功”。

每个文件明确分为可用、待修改或风险无效，并写清后续动作。权限、并发、事务和一致性要记录查了什么、依据哪条规约、结论是什么。发现共性问题后再完善对应规则，减少下一次重复生成同类问题。

后续每个增量都要把规约、审核意见、修复和验证证据串起来，再进入适用评审与合并流程。

## 6. 当前缺口与结束语（约40秒）

【回到核对清单，指向待补项】

目前八类规范和自动检查入口已经具备，但业务专项测试、完整的查询风险检查还需要随功能逐步补齐。项目负责人的人工逐段审核和独立同学交叉评审，也不能由这次AI辅助检查或CI代替。

这是单人项目，我会如实保留这些状态，请老师确认适配方式或安排同学复核，不把不同职责当成不同评审者。

下一阶段，我希望每项功能都能说明它为什么正确、在什么情况下可能失效、通过什么证据交付。也就是在已有工程起点上，逐步交付能力、审核记录和验证证据。
