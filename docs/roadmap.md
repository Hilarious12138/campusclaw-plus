# CampusClaw Plus：阶段规划与实践重点

规划更新：2026-11-03。项目面向班级教学，逐步连接讲义检索、辅助学习、作业批改和错题订正。基于GD经验独立建设，GD的完成状态不计入Plus。

本规划结合[下一阶段课件：审核AI写的代码](https://devops.hello1023.com/小组项目/小组项目下一阶段重点-AI代码审核.html)。后续不以页面数量作为主要进度，而以一项能力经过规约、审核和验证后可以交付作为进度。

## 已经完成什么，为什么先做这些

- **独立仓库和工程骨架**：先建立稳定起点，方便区分原有问题与新增问题。
- **四文档变更流程和八类规范**：先明确范围、验收标准和约束，减少AI生成后再解释需求的成本。
- **Docker自动验收及报告**：让他人能复验当前能力；失败和缺证据不能被当成成功。
- **PR与检查门禁**：让改动可回溯，把合入主干视为交付责任，而不是保存一份生成结果。

当前只有工程骨架与文档/工具入口。教学认证、检索、问答、作业与统计尚未在Plus实现；以下业务阶段均为计划，不承诺未经确认的日期。

每阶段先取最小完整能力建新change；具体接口、数值和实现选型写到对应design/spec，不在本路线图重复维护。技术栈继续React18/TypeScript/Vite、Go net/http、MySQL8、Nginx/Compose；向量、模型与MCP接入在相应阶段再确认。

## 每次交付要练的四件事

1. **说清保障**：这段实现要保证什么业务结果。
2. **找出保障机制**：由权限条件、状态规则、事务、唯一约束还是其他机制保证，不能只凭“先查过”。
3. **主动找失效条件**：换账号、重复请求、同时操作、中途失败与依赖不可达。
4. **修复后重新证明**：给出规约依据、可执行检查和实际结果，并将共性问题反馈到已有规则。

自动检查负责可重复判断的部分，人工重点读权限、事务、并发和数据一致性。已有工具覆盖静态分层、历史秘密、测试、依赖漏洞及运行验收；尚未具备业务查询扫描能力，不能把“工具跑绿”当成全面审核。

## 单人项目如何诚实记录

产品、开发、测试是同一人的不同职责。本人逐段审核、AI辅助检查、CI与另一位同学的交叉评审分别记录；前三者不能冒充最后一项。课件要求交叉评审，当前独立人类peer review仍未完成，需教师确认单人适配或安排同学复核。后续AI业务代码未满足审核及适用评审要求不得直接合入或上线。

规则见[review.md](../.agents/rules/review.md)，实际评审使用[同一份模板](reviews/template.md)。每次变更的审核、风险与处理结论留在docs/reviews，不另建重复的进度台账。
